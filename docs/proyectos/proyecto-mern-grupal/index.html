    Proyecto MERN Grupal

    Fundamentos teóricos

    El desarrollo de un proyecto web profesional implica no solo dominar las tecnologías de desarrollo, sino también comprender el contexto empresarial, planificar adecuadamente los recursos y seguir metodologías ágiles que garanticen entregas de valor constantes.

    El stack MERN

    Este proyecto se desarrollará utilizando el stack MERN, ampliamente adoptado en la industria del desarrollo web:

    • MongoDB: Base de datos NoSQL orientada a documentos, flexible y escalable.
    • Express.js: Framework minimalista para Node.js que facilita la construcción de APIs RESTful.
    • React: Biblioteca de JavaScript para construir interfaces de usuario interactivas y reactivas.
    • Node.js: Entorno de ejecución de JavaScript del lado del servidor.

    La ventaja principal del stack MERN es el uso de JavaScript en toda la pila, lo que permite a los desarrolladores trabajar con un único lenguaje en frontend y backend, facilitando la comunicación del equipo y la reutilización de código.

    Metodología SCRUM

    SCRUM es una metodología ágil que organiza el trabajo en sprints (iteraciones de 1-2-4 semanas) donde se diseñan, programan y testean nuevas funcionalidades. Los equipos son auto-organizados y el producto avanza de forma incremental.

    Roles principales:

    • Product Owner: Define prioridades y decide qué se incluye en cada sprint.
    • Scrum Master: Facilita las reuniones, documenta decisiones y elimina impedimentos.
    • Equipo de desarrollo: Realiza las tareas técnicas asignadas.

    Artefactos clave:

    • Product Backlog: Lista completa y priorizada de funcionalidades del producto.
    • Sprint Backlog: Tareas seleccionadas para el sprint actual.
    • Burndown Chart: Gráfico que muestra el progreso del equipo.

    Reuniones:

    • Daily Scrum: Reunión diaria de 15 minutos para sincronizar al equipo.
    • Sprint Planning: Planificación de las tareas del próximo sprint.
    • Sprint Review: Revisión del trabajo completado al final del sprint.
    • Sprint Retrospective: Reflexión sobre qué mejorar en el próximo sprint.

    Herramientas de gestión

    Para implementar SCRUM de manera efectiva, utilizaréis:

    • GitHub Projects: Gestión visual de tareas con campos personalizados (sprint, prioridad, estimación, categoría).
    • Toggl Track: Herramienta de seguimiento temporal para medir el esfuerzo real invertido en cada tarea.
    • GitHub Wiki: Documentación de la metodología, roles y actas de reuniones.

    Objetivos del proyecto

    • Aplicar el stack MERN en el desarrollo de una aplicación web completa.
    • Implementar metodología SCRUM con roles rotativos y reuniones definidas.
    • Analizar el contexto empresarial del proyecto (competencia, estructura organizativa, legislación).
    • Planificar y estimar recursos (humanos, materiales, económicos) de forma realista.
    • Gestionar el proyecto utilizando GitHub Projects y Toggl Track.
    • Documentar de manera profesional todo el proceso de desarrollo.

    Descripción del proyecto

    Este proyecto consiste en llevar a producción la propuesta grupal previamente diseñada, siguiendo una metodología profesional de gestión de proyectos.

    El proyecto se realizará en grupos de 3-4 personas y tendrá una duración de 6 sprints (aproximadamente 6 semanas).

    Fase 1: Análisis del sector y estructura empresarial

    Antes de comenzar el desarrollo, es fundamental comprender el contexto empresarial en el que se enmarca el proyecto.

    1a) Clasificación de empresas del sector (Criterio 1a)

    Objetivo: Investigar y clasificar empresas competidoras para conocer el mercado antes de lanzar el producto.

    Tareas:

    1. Identificación de competidores directos e indirectos:

      • Buscad al menos 5 empresas que ofrezcan productos o servicios similares.
      • Clasificadlas según:
        • Tamaño: Startup, PYME, gran empresa.
        • Modelo de negocio: B2C (Business to Consumer), B2B (Business to Business), C2C (Consumer to Consumer), freemium, suscripción, etc.
        • Alcance geográfico: Local, nacional, internacional.

    2. Análisis de características organizativas:

      • ¿Qué estructura tienen? (jerárquica, horizontal, matricial)
      • ¿Cuántos empleados tienen aproximadamente?
      • ¿Qué tecnologías utilizan? (si es información pública)

    3. Análisis del producto/servicio:

      • Funcionalidades principales.
      • Propuesta de valor única.
      • Precios y condiciones comerciales.
      • Puntos fuertes y débiles.

    4. Documentación:

      • Cread un documento /docs/analisis-competencia.md en vuestro repositorio.
      • Incluid una tabla comparativa con las empresas analizadas.
      • Añadid conclusiones sobre oportunidades detectadas.

    1b) Estructura organizativa de la empresa (Criterio 1b)

    Objetivo: Diseñar la estructura organizativa que tendría la empresa si llevarais el proyecto a producción real.

    Tareas:

    1. Definición de la estructura empresarial:

      • Imaginad que vuestro proyecto se convierte en una empresa real.
      • ¿Qué tipo de empresa sería? (Startup tecnológica, SaaS, etc.)
      • ¿Qué estructura organizativa adoptaríais?

    2. Identificación de departamentos y funciones:

      • Ejemplos de departamentos típicos en una empresa tecnológica:
        • Dirección/Gerencia: Define la estrategia, toma decisiones clave.
        • Departamento de Desarrollo:
          • CTO (Chief Technology Officer): Responsable técnico, define arquitectura.
          • Frontend Developers: Desarrollo de interfaces de usuario.
          • Backend Developers: Desarrollo de APIs y lógica de negocio.
          • DevOps Engineers: Gestión de infraestructura, CI/CD, despliegues.
          • QA Engineers: Testing, control de calidad.
        • Departamento de Producto:
          • Product Manager: Define roadmap, prioriza funcionalidades.
          • UX/UI Designers: Diseño de experiencia de usuario e interfaces.
        • Departamento de Marketing y Ventas:
          • Marketing Manager: Estrategias de captación de usuarios.
          • Community Manager: Gestión de redes sociales y comunidad.
          • Sales Team: Ventas y relación con clientes (si aplica).
        • Departamento de Atención al Cliente:
          • Customer Support: Soporte técnico y atención a usuarios.
        • Departamento de Administración:
          • CFO (Chief Financial Officer): Gestión financiera.
          • HR Manager: Recursos humanos, contratación.
          • Legal/Compliance: Aspectos legales, protección de datos.

    3. Organigrama:

      • Cread un organigrama visual con la estructura propuesta.
      • Herramientas sugeridas: draw.io, Mermaid.

    4. Justificación:

      • Explicad por qué habéis elegido esa estructura.
      • ¿Qué tamaño de equipo necesitaríais inicialmente?
      • ¿Cómo escalaría la empresa con el tiempo?

    5. Documentación:

      • Cread un documento /docs/estructura-organizativa.md en vuestro repositorio.
      • Incluid el organigrama y la descripción de funciones de cada departamento.

    Fase 2: Planificación del proyecto con SCRUM

    Una vez comprendido el contexto empresarial, es momento de planificar el desarrollo del proyecto usando metodología SCRUM.

    2c) Identificación de fases del proyecto (Criterio 2c)

    Objetivo: Dividir el proyecto en 6 sprints claramente definidos, con objetivos específicos para cada uno.

    Tareas:

    1. Definición de sprints:

      • El proyecto tendrá 6 sprints de 1 semana cada uno.
      • Cada sprint debe tener un objetivo claro y medible.
      • Ejemplo de estructura de sprints:
        • Sprint 1 - Setup y arquitectura base:
          • Configuración del repositorio, estructura de carpetas.
          • Configuración inicial de MongoDB, Express, React, Node.js.
          • Diseño de esquemas de base de datos.
          • Configuración de entorno de desarrollo (ESLint, Prettier, variables de entorno).
        • Sprint 2 - Autenticación y roles de usuario:
          • Sistema de registro y login.
          • Gestión de sesiones (JWT).
          • Roles de usuario (admin, usuario estándar, etc.).
          • Protección de rutas.
        • Sprint 3 - Funcionalidades principales (parte 1):
          • Implementación de las 2-3 funcionalidades core del MVP.
          • CRUD de las entidades principales.
        • Sprint 4 - Funcionalidades principales (parte 2):
          • Completar funcionalidades del MVP.
          • Integración con APIs externas si aplica.
        • Sprint 5 - Testing y optimización:
          • Tests unitarios y de integración.
          • Testing visual con Maestro.
          • Optimización de rendimiento.
          • Refactorización de código.
        • Sprint 6 - Despliegue y documentación final:
          • Configuración de hosting y base de datos en producción.
          • Despliegue continuo con CI/CD.
          • Documentación técnica completa.
          • Preparación de la presentación final.

    2. Configuración en GitHub Projects:

      • Cread un campo de tipo iteración (será el sprint) en GitHub Projects.
      • Asignad cada tarea/issue al sprint correspondiente.
      • Definid las fechas de inicio y fin de cada sprint.

    3. Definición de entregables por sprint:

      • Cada sprint debe tener entregables concretos (funcionalidades, componentes, documentación).
      • Documentad estos entregables en la Wiki del repositorio.

    4. Documentación:

      • Cread una página en la Wiki del repositorio: Planificación de Sprints.
      • Incluid una tabla con los 6 sprints, fechas, objetivos y entregables esperados.

    2f) Presupuesto económico (Criterio 2f)

    Objetivo: Realizar una estimación económica del proyecto basada en el tiempo invertido.

    Tareas:

    1. Estimación de horas por tarea:

      • En GitHub Projects, añadid un campo personalizado "Estimación (horas)".
      • Estimad cuántas horas llevará cada tarea ANTES de comenzarla.
      • Utilizad técnicas como Planning Poker (busca información sobre la misma) en las reuniones de Sprint Planning.

    2. Medición de horas reales con Toggl Track:

      • Cada miembro del equipo debe usar Toggl Track para registrar el tiempo real invertido.
      • Seguid el flujo de trabajo propuesto en las diapositivas:
        1. Abrir tarea en GitHub.
        2. Arrancar timer en Toggl Track.
        3. Trabajar en la tarea.
        4. Añadir comentario en el issue explicando el progreso.
        5. Parar timer al terminar o hacer pausa.

    3. Cálculo del coste del proyecto:

      • Definid un coste/hora por perfil:
      • Junior Developer: 15-25 €/hora.
      • Mid Developer: 30-45 €/hora.
      • Senior Developer: 50-80 €/hora.
      • Al final de cada sprint, calculad el coste real multiplicando las horas trabajadas por el coste/hora.

    4. Comparación estimación vs. realidad:

      • Comparad las horas estimadas con las horas reales.
      • Identificad las tareas que han llevado más tiempo del previsto y analizad por qué.
      • Usad esta información para mejorar las estimaciones en sprints futuros.

    5. Presupuesto total del proyecto:

      • Sumad los costes de todos los sprints.
      • Añadid costes adicionales:
        • Servicios externos (hosting, dominios, APIs de pago).
        • Licencias de software (si aplica).
        • Marketing inicial (si se contempla).

    6. Documentación:

      • Cread un documento /docs/presupuesto.md en vuestro repositorio.
      • Incluid:
        • Tabla con estimaciones de horas por sprint.
        • Costes calculados por sprint.
        • Comparación estimación vs. realidad (actualizar al final de cada sprint).
        • Presupuesto total del proyecto.

    2g) Necesidades de financiación (Criterio 2g)

    Objetivo: Identificar qué necesidades de financiación tendría el proyecto para su puesta en marcha real.

    Tareas:

    1. Costes iniciales de desarrollo:

      • Basándoos en el presupuesto calculado en 2f, identificad el coste total de desarrollo.
      • ¿Podríais afrontar este coste sin financiación externa?

    2. Costes de infraestructura y servicios:

      • Hosting: ¿Qué servicio usaréis? (DigitalOcean, AWS, Vercel, Railway, Render, etc.)
        • Calculad el coste mensual estimado.
      • Base de datos: ¿MongoDB Atlas gratuito es suficiente o necesitaréis un plan de pago?
      • Dominio: Coste anual (~10-15 €/año).
      • APIs externas: ¿Alguna tiene límites gratuitos insuficientes?
      • CDN, almacenamiento de archivos: Si aplica (ej: AWS S3, Cloudinary).
      • Servicios de email: Si necesitáis enviar emails transaccionales (ej: SendGrid, Mailgun).
      • Monitorización y logs: Servicios como Sentry, Datadog (suelen tener planes gratuitos limitados).

    3. Costes de marketing y lanzamiento:

      • ¿Necesitaríais invertir en publicidad inicial? (Google Ads, redes sociales)
      • ¿Coste de diseño de marca? (logo, identidad visual)

    4. Capital de trabajo:

      • Durante los primeros meses, es probable que no haya ingresos.
      • ¿Cuánto tiempo podría operar la empresa sin ingresos?
      • Calculad un fondo de emergencia (recomendado: 6 meses de gastos fijos).

    5. Fuentes de financiación:

      • Investigad posibles fuentes de financiación para startups tecnológicas:
        • Autofinanciación (ahorros personales, "bootstrapping").
        • Préstamos bancarios: ¿Condiciones? ¿Avales necesarios?
        • Ayudas y subvenciones públicas: Investigad programas como Enisa, ICO, ayudas autonómicas.
        • Business Angels: Inversores privados que aportan capital y experiencia.
        • Venture Capital (VC): Fondos de capital riesgo para proyectos con alto potencial de crecimiento.
        • Crowdfunding: Plataformas como Kickstarter, Verkami.
        • Aceleradoras e incubadoras: Programas que ofrecen financiación, mentoría y contactos (ej: Lanzadera, Plug and Play).

    6. Plan de financiación propuesto:

      • Basándoos en el análisis anterior, proponed un plan de financiación realista.
      • ¿Cuánto capital necesitaríais captar?
      • ¿Qué fuente de financiación es más adecuada para vuestro proyecto?
      • ¿En qué lo invertiríais? (desarrollo, marketing, infraestructura, etc.)

    7. Documentación:

      • Cread un documento /docs/financiacion.md en vuestro repositorio.
      • Incluid:
        • Desglose de costes de infraestructura y servicios.
        • Necesidades de capital de trabajo.
        • Fuentes de financiación analizadas.
        • Plan de financiación propuesto con justificación.

    Fase 3: Ejecución y gestión del proyecto

    Una vez planificado el proyecto, es momento de ejecutarlo siguiendo las mejores prácticas de gestión ágil.

    3a) Secuenciación y priorización de actividades (Criterio 3a)

    Objetivo: Organizar las tareas en orden lógico según las necesidades de ejecución y asignar prioridades.

    Tareas:

    1. Identificación de dependencias:

      • Algunas tareas no pueden comenzar hasta que otras estén terminadas.
      • Ejemplo: No puedes implementar el sistema de autenticación de usuarios hasta que la estructura básica del backend esté lista.
      • Identificad estas dependencias y documentadlas en los issues de GitHub.

    2. Definición de prioridades:

      • Cread un campo personalizado "Prioridad" en GitHub Projects con valores de 1 hasta infinito. De forma que una persona no tenga una tarea con la misma prioridad en un mismo sprint.

    3. Ordenación del Product Backlog:

      • El Product Owner debe ordenar el Product Backlog por prioridad.
      • Las tareas críticas y de alta prioridad deben estar en los primeros sprints.

    4. Columnas en GitHub Projects:

      • Cread las siguientes columnas (mínimo):
        • Backlog: Tareas pendientes de planificar.
        • To Do: Tareas del sprint actual, listas para comenzar.
        • In Progress: Tareas en desarrollo.
        • In Review: Tareas completadas pendientes de revisión (PR abierta).
        • Done: Tareas completadas y revisadas.

    5. Flujo de trabajo:

      • Cada miembro del equipo trabaja en la tarea de máxima prioridad que tenga asignada.
      • Al terminar una tarea, se avanza a la siguiente por prioridad.

    6. Documentación:

      • El tablero de GitHub Projects debe reflejar claramente las prioridades.
      • En la Wiki, documentad el criterio de priorización que habéis establecido.

    3b) Asignación de recursos y logística (Criterio 3b)

    Objetivo: Asignar recursos humanos a cada tarea y estimar el esfuerzo necesario.

    Tareas:

    1. Identificación de perfiles necesarios:

      • Para cada tarea, identificad qué perfil es el más adecuado:
        • Frontend: Desarrollo de componentes React, estilos, interacción.
        • Backend: APIs, lógica de negocio, integración con base de datos.
        • Full Stack: Tareas que requieren trabajar en ambas capas.
        • DevOps: Configuración de CI/CD, despliegues, monitorización.
        • QA/Testing: Pruebas, detección de bugs, testing visual.

    2. Asignación de tareas en GitHub Projects:

      • Cada issue debe tener un responsable asignado (assignee).
      • En el Sprint Planning, el equipo decide quién se encarga de cada tarea.
      • Tened en cuenta la estimación para que el número de horas que suman todas las tareas asignadas a una persona en un sprint esté equilibrado con el resto del equipo.

    3. Estimación de esfuerzo:

      • Usad técnicas de estimación en equipo:
        • Planning Poker (busca más información al respecto): Cada miembro estima la tarea con una carta (números de Fibonacci: 1, 2, 3, 5, 8, 13).
        • Se discuten las diferencias y se llega a un consenso.
        • Registrad la estimación en el campo "Estimación (horas)" de GitHub Projects.

    4. Balanceo de carga:

      • El Scrum Master debe vigilar que la carga de trabajo esté equilibrada.
      • Si alguien está bloqueado o sobrecargado, se redistribuyen tareas.

    5. Recursos materiales y herramientas:

      • Identificad las herramientas necesarias para cada tarea:
        • Editores de código (VS Code, IntelliJ IDEA)
        • Herramientas de diseño (Figma, Sketch) si es necesario.
        • Software de pruebas (Postman para APIs, Maestro para UI).
        • Servicios externos (cuentas en MongoDB Atlas, servicios de hosting).

    6. Documentación:

      • Mantened actualizado el tablero de GitHub Projects con las asignaciones.
      • En la Wiki, documentad:
        • Qué perfiles tiene cada miembro del equipo.
        • Qué herramientas se están utilizando.
        • Cómo se realiza la estimación de tareas.

    3c) Identificación de permisos, autorizaciones y legislación (Criterio 3c)

    Objetivo: Analizar qué legislación debe cumplir la aplicación para poder operar legalmente.

    Tareas:

    1. Protección de datos - RGPD:

      • Si la aplicación recoge datos personales de usuarios europeos, debe cumplir el Reglamento General de Protección de Datos (RGPD).
      • Aspectos a implementar:
        • Consentimiento explícito: Los usuarios deben aceptar la recogida de sus datos.
        • Información transparente: Política de privacidad clara y accesible.
        • Derechos de los usuarios: Acceso, rectificación, supresión, portabilidad de datos.
        • Seguridad de los datos: Cifrado de contraseñas (bcrypt), comunicaciones HTTPS.
        • Delegado de Protección de Datos (DPO): Necesario en ciertos casos (empresas grandes, tratamiento masivo de datos).

    2. Política de cookies:

      • Si la aplicación utiliza cookies (sesiones, analytics, publicidad), necesitáis:
        • Banner de cookies: Informar al usuario y solicitar consentimiento.
        • Clasificación de cookies: Técnicas, de personalización, analíticas, publicitarias.
        • Gestión de preferencias: Permitir al usuario aceptar/rechazar cookies no esenciales.

    3. Condiciones de uso y términos de servicio:

      • Documento legal que establece:
        • Qué pueden y no pueden hacer los usuarios.
        • Limitaciones de responsabilidad.
        • Propiedad intelectual del contenido.
        • Causas de suspensión de cuenta.

    4. Accesibilidad web:

      • En muchos países (incluida España), las webs públicas y de empresas deben cumplir criterios de accesibilidad.
      • Norma de referencia: WCAG 2.1 (Web Content Accessibility Guidelines).
      • Aspectos a tener en cuenta:
        • Contraste de colores adecuado.
        • Navegación por teclado.
        • Etiquetas alt en imágenes.
        • Estructura semántica correcta (HTML5).
        • Compatibilidad con lectores de pantalla.

    5. Propiedad intelectual:

      • Si usáis imágenes, iconos, fuentes o cualquier recurso de terceros:
        • Verificad que tenéis licencia de uso.
        • Usad recursos con licencias libres (Creative Commons, iconos de Font Awesome, etc.).
      • Si integráis APIs externas, revisad sus términos de servicio.

    6. Normativa específica del sector:

      • Dependiendo del tipo de aplicación, puede haber normativas adicionales:
        • E-commerce: Ley de Servicios de la Sociedad de la Información y de Comercio Electrónico (LSSI-CE), devoluciones, derecho de desistimiento.
        • Salud: Si manejáis datos de salud, regulación muy estricta (HIPAA en EE.UU., normativa específica en cada país).
        • Finanzas: Si procesáis pagos, normativas PCI-DSS, licencias de entidad de pago.
        • Contenido generado por usuarios: Moderación de contenido, responsabilidad por contenido ilícito.

    7. Permisos y autorizaciones:

      • ¿Necesitáis algún permiso específico para operar?
        • Ejemplo: Si ofrecéis servicios educativos, puede haber regulación específica.
      • ¿Necesitáis registros oficiales?
        • Ejemplo: Alta en el Registro de Protección de Datos si procesáis datos sensibles.

    8. Implementación técnica de cumplimiento legal:

      • Política de privacidad: Cread una página /legal/privacidad con el texto legal.
      • Política de cookies: Cread una página /legal/cookies y un banner que se muestre al entrar.
      • Términos de uso: Cread una página /legal/terminos.
      • Checkbox de aceptación: En formularios de registro, incluir checkbox de aceptación de políticas.
      • Gestión de datos personales: Implementad endpoints para que los usuarios puedan:
        • Ver sus datos (exportación JSON).
        • Solicitar borrado de cuenta (eliminación de datos).

    9. Documentación:

      • Cread un documento /docs/legislacion.md en vuestro repositorio.
      • Incluid:
        • Listado de normativas aplicables a vuestro proyecto.
        • Requisitos específicos de cada normativa.
        • Plan de implementación técnica para cumplir con la legislación.
        • Borradores o enlaces a las políticas legales (privacidad, cookies, términos).

    3f) Planificación de recursos materiales, humanos y tiempos (Criterio 3f)

    Objetivo: Consolidar toda la planificación de recursos y tiempos en GitHub Projects.

    Tareas:

    1. Configuración completa de GitHub Projects:

      • Aseguraos de que el tablero tiene todos los campos personalizados:
        • Sprint: A qué sprint pertenece la tarea.
        • Prioridad: De 1 (máxima) a infinito.
        • Estimación (horas): Horas estimadas para completar la tarea.
        • Categoría: Frontend, Backend, BD, DevOps, Testing, Documentación.
        • Estado: Backlog, To Do, In Progress, In Review, Done.
        • Asignación: Persona responsable.

    2. Planificación de tiempos:

      • Definid fechas de inicio y fin de cada sprint.
      • Calculad la velocidad del equipo (recomendado una semana):
        • Al finalizar cada sprint, sumad las horas estimadas de las tareas completadas.
        • Esto os dará una idea de cuánto trabajo podéis asumir en el siguiente sprint.

    3. Gestión de riesgos temporales:

      • Identificad tareas que podrían retrasarse (tareas complejas, dependencias externas).
      • Dejad un buffer de tiempo (10-20% del sprint) para imprevistos.

    4. Recursos humanos:

      • Documentad en la Wiki los roles rotativos:
        • Tabla con los sprints y quién asume cada rol (Product Owner, Scrum Master, Dev).
      • Todos los miembros deben rotar por los roles a lo largo de los 6 sprints.

    5. Recursos materiales:

      • Mantened actualizado el documento /docs/recursos.md con:
        • Servicios contratados (hosting, base de datos, dominios).
        • APIs utilizadas y sus límites.
        • Credenciales y accesos compartidos (usando un gestor de contraseñas del equipo, ej: 1Password, Bitwarden).

    6. Documentación:

      • Aseguraos de que GitHub Projects está actualizado en todo momento.
      • El Scrum Master es responsable de mantener el tablero al día.
      • Cread en la Wiki una página: Gestión de Recursos y Tiempos.

    3g) Valoración económica de la implementación (Criterio 3g)

    Objetivo: Realizar un análisis económico completo del proyecto al finalizar su implementación.

    Tareas:

    1. Análisis de costes reales:

      • Al finalizar cada sprint, actualizad el documento /docs/presupuesto.md con:
        • Horas reales trabajadas (extraídas de Toggl Track).
        • Costes reales calculados.
        • Desviaciones respecto a la estimación inicial.

    2. Costes totales del proyecto:

      • Al finalizar los 6 sprints, calculad:
        • Coste total de desarrollo (suma de costes de todos los sprints).
        • Costes de infraestructura (servicios contratados durante el desarrollo).
        • Costes adicionales (herramientas, licencias, etc.).

    3. Valoración del producto final:

      • ¿Cuánto valdría el producto en el mercado?
      • Investigad productos similares: ¿A qué precio se venden o se licencian?
      • Si es un SaaS: ¿Qué precio de suscripción sería competitivo?

    4. Retorno de inversión (ROI):

      • Si se lanzara el producto: ¿Cuánto tiempo tardaría en recuperar la inversión?
      • Calculad escenarios:
        • Escenario optimista: Muchos usuarios desde el inicio.
        • Escenario realista: Crecimiento moderado.
        • Escenario pesimista: Pocos usuarios al principio.

    5. Lecciones aprendidas sobre gestión económica:

      • ¿Fueron precisas las estimaciones iniciales?
      • ¿Qué tareas costaron más de lo esperado? ¿Por qué?
      • ¿Hubo costes imprevistos?
      • ¿Qué haríais diferente en un próximo proyecto?

    6. Documentación final:

      • Actualizad /docs/presupuesto.md con:
        • Tabla de costes reales por sprint.
        • Coste total del proyecto.
        • Comparación estimación inicial vs. coste real.
        • Análisis de desviaciones.
        • Valoración del producto y análisis de ROI.
        • Lecciones aprendidas.

    Recomendaciones finales

    1. Comunicación constante: Mantened comunicación diaria entre el equipo, no solo en las Daily Scrums.

    2. Documentad todo: La documentación es clave para la evaluación. No basta con hacer el trabajo, hay que documentarlo adecuadamente.

    3. Seguid el flujo de trabajo: Respetad el flujo propuesto (issue → rama → timer → trabajo → comentario → PR).

    4. Rotación de roles: Aseguraos de que todos los miembros roten por los roles de Product Owner y Scrum Master.

    5. Revisiones de código: Implementad revisiones de código obligatorias (code reviews) en las Pull Requests antes de mergear a main.

    6. Testing continuo: No dejéis el testing para el final. Implementad tests desde el principio.

    7. Commits frecuentes: Haced commits pequeños y frecuentes con mensajes descriptivos.

    8. Retrospectivas honestas: Utilizad las Sprint Retrospectives para mejorar realmente el proceso, sed honestos sobre lo que no funciona.

    9. Gestión de bloqueos: Si alguien está bloqueado, debe comunicarlo inmediatamente en la Daily o en el canal del equipo.

    10. Celebrad los logros: Al completar cada sprint, celebrad lo conseguido. El trabajo en equipo debe ser también gratificante.
